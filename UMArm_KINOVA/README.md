## Set it up (once)

```
python UMArm_KINOVA/setup_env.py            # create/repair, then self-test
python UMArm_KINOVA/setup_env.py --check    # verify only, change nothing
```

That builds `.venv_kinova/` at the repo root and installs the committed Kortex
wheel into it. **Every Kinova entry point runs with that interpreter**, not with
bare `python`:

```
.venv_kinova/Scripts/python.exe UMArm_KINOVA/kinova_arm.py
```

### Why a separate environment

`kortex_api` 2.6.0.post3 is not on PyPI, its message stubs were generated by
protoc 3.5, and it therefore hard-pins `protobuf==3.5.1` — a 2017 release that
would break anything else in this repo wanting protobuf. Since that protobuf
predates Python 3.10 it also reaches for `collections.MutableMapping`, removed in
3.10, so it cannot even be imported without a patch; `setup_env.patch_protobuf_abc`
applies that patch mechanically and idempotently, which is the difference between
an environment that can be rebuilt and one that has to be remembered. Verified on
CPython 3.13.13; the lab also runs it on 3.11.9 and 3.12.10.

## The arm

| fact | value |
|---|---|
| address | `192.168.1.10`, `admin` / `admin` |
| this PC | `192.168.1.120` on the same private network as the cameras |
| web app | <http://192.168.1.10> — clear faults here when a move silently no-ops |
| units | **metres and degrees**; a pose is `[x, y, z, theta_x, theta_y, theta_z]`, intrinsic-xyz Euler, in the **base** frame |
| configured tool transform | `(10, 0, 5) mm`, no rotation — read it, do not assume it |

That last row matters more than it looks. `tool_pose_*` is the pose of the arm's
configured TOOL frame, not of the bare flange, so an offset left in the
controller by an earlier project silently redefines every number fitted against
it. `kinova_arm.tool_configuration` reads it and every campaign record stores it.

## Use it

```python
from UMArm_KINOVA.kinova_arm import SafeKinovaArm

with SafeKinovaArm() as arm:
    arm.arm_envelope()                       # centre the keep-out ball here
    print(arm.snapshot())                    # pose + joints from ONE feedback read
    arm.move_to_pose(target, speed_ms=0.03)  # envelope-checked, speed-limited, blocking
```

`SafeKinovaArm` wraps the lab's portable driver (`vendor/`) and adds the three
things this lab needs and the portable driver deliberately does not have: a
keep-out ball that **refuses** rather than clips, an explicit speed on every pose
move, and a `snapshot()` that reads the tool pose and the seven joint angles out
of one `RefreshFeedback` so the two halves of a record are the same instant.

An unarmed envelope refuses everything — forgetting to arm it stops the run
instead of removing the limit.

`send_twist` is refused by name on the wrapper and always will be: a velocity has
no target pose, so the envelope has nothing to pre-check, and an unchecked mover
one attribute lookup away is one somebody will reach for. **One caller reaches it
on purpose**, `SafeKinovaArm.twist_checked`, and owns the limit there:

```python
arm.twist_checked(linear=[0, 0, 0.03], angular=[0, 0, 0])   # m/s, deg/s
arm.stop()                                                  # not optional
```

It reads the live pose every call and measures it against the keep-out ball, so
the guard is a **poll at the caller's rate** rather than a pre-check. At the wall
it drops the *outward* component of the velocity and passes the tangential and
inward parts — refusing outright would leave Home, the one move that is not
envelope-checked, as the only way back out. Magnitudes are clamped to
`TWIST_LIN_CEIL_MS` = 0.10 m/s and `TWIST_ANG_CEIL_DEG_S` = 40 deg/s, which are
the simulated task-space jog's own top speeds.

The cost is stated rather than hidden: a twist is checked where the arm *is*, not
where it is going, so between two calls the arm travels `v · dt` unchecked — 1.5 mm
at the bridge's 40 Hz and its fastest 0.06 m/s preset.

### The bridge, and why it exists

The collision bench's GUI runs under the ordinary interpreter, with a MuJoCo and
a NumPy that 2017's protobuf would not survive sharing a process with. So the
real arm is reached the way any other cross-runtime device is: a child process on
the interpreter that *can* import the driver, and one line of JSON per message.

```
.venv_kinova/Scripts/python.exe UMArm_KINOVA/arm_bridge.py
{"cmd": "connect"}
{"cmd": "arm", "on": true}
{"cmd": "jog", "d_xyz": [0, 0, 1], "speed": "slow"}
{"cmd": "jog_start", "d_xyz": [0, 0, 1], "speed": "slow", "frame": "robot"}
{"cmd": "jog_stop"}
{"cmd": "stop"}
```

| command | what it does |
|---|---|
| `connect` / `disconnect` | opens or closes the Kortex session. `connect` also asks for a mocap receiver, on a worker; it does **not** wait for one |
| `arm` `{on}` | centres the keep-out ball on wherever the arm is standing. Nothing moves until this has been sent |
| `stop` | disarms, kills any held jog, and stops the arm. Always accepted, and always the last thing the arm hears |
| `joints` `{values_deg}` | one bounded `move_joints`, leashed to `MAX_JOINT_STEP_DEG` per actuator |
| `home` | the arm's own Home. Checked against the joints it asks for, not against a completion flag |
| `jog` `{d_xyz, d_rpy_deg, speed}` | one bounded `move_delta` of a stated DISTANCE, which finishes and reports |
| `jog_start` `{d_xyz, d_rpy_deg, speed, frame}` | **the heartbeat of a held button.** Opens a ramped Cartesian twist; repeat at ≤ 350 ms to keep it alive |
| `jog_stop` | let go. Not an error when nothing is held |
| `mocap` `{on}` | start or stop the receiver without touching the arm session |
| `mocap_solve_base` | re-derive `X = T_world_base` from one still mocap frame plus the arm's own pose |
| `ping`, `quit` | as they read |

**The safety model is in the bridge, not in the caller**, because that is the
only place a limit cannot be skipped by somebody who forgot the wrapper:

* **connect and arm are two steps.** Connect opens the session and reports; it
  cannot move the arm. Arm centres `SafeKinovaArm.arm_envelope` on wherever the
  arm is standing, and every motion command is refused until it has been sent;
* **a joint move is leashed too.** The envelope is Cartesian and `move_joints`
  leaves Cartesian space, which is why `SafeKinovaArm` refuses it by name;
  reaching it deliberately means owning the limit here, so `MAX_JOINT_STEP_DEG`
  = 30 deg refuses a command that would move any actuator further than that from
  where it is now — wrapped, because joints 1/3/5/7 are continuous;
* **one motion at a time, on a worker**, so `stop` lands while a move is
  running. That is the one message that has to get through. A held jog holds
  `busy` exactly as a joint move does, so the two cannot both run;
* **a failed or refused move disarms**, because the arm is no longer where the
  envelope was centred;
* **one thing streams, and it is a dead-man.** `jog_start` is a velocity, and a
  Kortex twist has no end of its own — `cmd.duration = 0`, and the vendored
  driver has no watchdog. Three guards, and all three have to fail before the arm
  keeps moving: the jog expires `JOG_DEADMAN_S` = 350 ms after the last
  heartbeat (three missed beats at the panel's 100 ms repeat), the driving thread
  dies on the stop epoch and issues its own `arm.stop()` on the way out, and
  every slice re-polls the live pose against the ball. A **lost** release
  therefore costs a coast and not a runaway: 27.8 mm at `fast`, 13.9 at `normal`,
  4.9 at `slow`, measured by integrating the shipped ramp at its 40 Hz.

`bridge_client.KinovaLink` is the host side and is shaped like
`UMArm_COLLAB.gui.launcher.BenchLauncher` — `start`, `send`, `poll`, `describe`,
`shutdown` — because it is the same kind of object: a child process a GUI event
loop owns.

### The cameras, inside the bridge

The receiver lives in the bridge process rather than beside the GUI, because that
is the only arrangement in which a world-frame command is arithmetic on local
variables: the operator's direction, `arm.snapshot()`, `rx.kinova_window()` and
the two calibration transforms are then all in one place and all one instant.
Measured here: `Base_pb2` (0.028 s) and `kinova_mocap` (0.069 s) import into one
process without complaint, and `MocapRx.start()` then returns in 0.0107 s with
120.0 Hz of rigid body 1008 arriving.

**It is optional in the strong sense.** No Motive, no `UMArm_MOCAP`, a wrong
client IP, a body that is not streamed — each is a published state, not an error,
and the arm stays fully usable in its own base frame through all of them.
`Bridge.state()` carries a `mocap` block whether or not an arm is connected.

Two riders, both measured on this machine and both handled:

* **the SDK's threads are not daemons.** A receiver started and never stopped
  kept a script alive past a 15 s timeout (`EXIT=124`). `serve` stops it in its
  `finally`, and a `stop` that races a `start` is joined rather than abandoned;
* **the SDK prints to stdout, from its own threads, whenever it likes.** Those
  lines would land in the middle of the JSON protocol. `sys.stdout` is redirected
  to stderr for the receiver's whole life — not merely around `start()`, which
  was measured to leak — and `arm_bridge._JSON_OUT` holds the channel's file
  object from before any of it, so no redirect can move it.

### The world frame, and why `X` is re-solved every session

`Y = T_tool_rb` is loaded from the newest `analysis.json`. **`X = T_world_base` is
not.** It is where the cart is parked, it dies the moment the cart is dragged, and
nothing the cameras can see distinguishes a cart that has moved from an arm that
has. So `mocap_solve_base` re-derives it from one still frame plus the arm's own
forward kinematics (`X = N Y⁻¹ M⁻¹`) and reports the disagreement with the stored
one in millimetres and degrees — **that number is the health indicator for the
whole world-frame option**. On a campaign sample the single-frame solve reproduced
the fitted `X` to 0.891 mm / 0.1297 deg, and the campaign's own `base_recovery`
spread is 2.07 mm RMS with a 6.97 mm maximum; centimetres means the cart moved.

A world-frame jog rotates the operator's direction into the base with `R_X^T`,
using the session's `X` and never the stored one, and is then commanded as an
ordinary base-frame twist through the same envelope poll. The world frame is
offered only when three things hold at once: frames arriving, `Y` loaded, and an
`X` solved this session and less than `BASE_SOLVE_TTL_S` = 15 min old.

## The two transforms, and which one you want

```
T_world_rb(i)  =  X . T_base_tool(i) . Y
```

* **`Y = T_tool_rb`** is where Motive's rigid-body frame sits on the tool. It is
  a property of how the markers are glued on, so it survives cart moves and
  power cycles. It is the number you almost always want.
* **`X = T_world_base`** is where the cart is parked, and dies the moment the
  cart is dragged. With `Y` known, one still mocap frame plus the arm's own
  forward kinematics recovers it — no re-calibration.

Current values, both campaigns of 2026-08-19 agreeing to 0.025 mm and 0.015 deg:

```
Y   translation  -10.336   65.849   51.801 mm   (84.42 mm lever)
    rotation     -89.794  -28.727    1.276 deg  (extrinsic xyz)
```

## Commanding the sensor frame

This is what the calibration is for. A pose written in the cameras' coordinates
inverts straight back to one the arm accepts, so "put the sensor frame here, in
the volume" is one Cartesian move:

```
.venv_kinova/Scripts/python.exe UMArm_KINOVA/sensor_frame.py --where
.venv_kinova/Scripts/python.exe UMArm_KINOVA/sensor_frame.py \
    --move-world 0.03 -0.02 0.015 --back --yes
```

`--move-world` reads the rigid body before and after and reports what it
actually achieved, because a prediction nobody checks is a prediction nobody
should trust. Measured 2026-08-19: asked for (30, -20, 15) mm and got it to
0.12 mm; asked for 12 deg about the sensor's own origin and the origin moved
0.19 mm.

## Running the campaign

```
.venv_kinova/Scripts/python.exe UMArm_KINOVA/calibrate_mocap.py --dry-run   # prints the plan, touches nothing
.venv_kinova/Scripts/python.exe UMArm_KINOVA/calibrate_mocap.py --yes       # ~6 min, MOVES THE ARM
```

Clear the workspace first. The plan stays inside a 20 cm-diameter ball about
Home, every move is speed-limited to 30 mm/s and blocking, every arrival is
verified, and the arm is sent Home at the end whatever happened.

**It needs rotation as well as translation, and that is not optional.** A
campaign of pure translations cannot see the marker body's rotation or the lever
arm from the tool to it — both cancel out of every translation — and would
return a beautiful residual with an arbitrary `Y`.
`mocap_calibration.observability` reports that condition rather than letting it
through.

## Gotchas

* Pose moves silently no-op if the arm is in a fault state. Clear faults in the
  web app.
* `protobuf` must stay at 3.5.1 in `.venv_kinova`. A newer one breaks the Kortex
  stubs at import; if you see descriptor errors, that is what happened.
* Motive's marker slot order is **not** this repo's order. It is
  `mount_transforms.PAD_MARKER_MOTIVE_SLOTS = (3, 1, 2, 0)`; use
  `reorder_motive_pad_markers` before handing markers to a pose fit.
* `mocap_calibration.py` imports nothing from `kortex_api`, so its tests run
  under the ordinary interpreter:
  `python -m pytest UMArm_KINOVA/test_mocap_calibration.py -q`.
